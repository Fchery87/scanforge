# System Overview

## Purpose

ScanForge is the orchestration layer around multiple security scanners. It does not try to replace those tools. It manages repository onboarding, scan execution, normalized storage, triage workflow, notifications, exports, and auditability.

## Runtime Topology

- browser -> Next.js web app
- web app -> FastAPI API
- API -> Postgres for system-of-record data
- API -> Upstash Redis REST queue for scan jobs and transient job status
- worker -> internal API routes for scan coordination
- worker -> GitHub repository clone flow
- worker -> scanner binaries on disk
- worker -> S3-compatible object storage for raw artifacts and uploaded files

## Core Flow

1. A user creates or joins an organization.
2. The user creates a project.
3. The organization connects GitHub.
4. The user connects repositories to the project.
5. The API creates scan records and enqueues jobs.
6. The worker clones the repository and runs the selected scanners.
7. The worker uploads raw artifacts and persists normalized findings.
8. Users review findings, schedules, notifications, exports, and scorecards in the web app.

## Scan Lifecycle

```text
queued -> running -> completed
                  -> failed
                  -> canceled
```

The worker also tracks per-job retry metadata in the queue layer and can move jobs to a dead-letter queue path after repeated failures.

## Current Scanner Coverage

- Trivy
- Gitleaks
- OSV-Scanner
- Semgrep
- Syft
- Checkov
- Grype

Not every scan type runs every scanner. The worker chooses a scanner subset based on the requested scan mode.

## Core Data Relationships

```text
User
  -> OrganizationMember
  -> Organization
  -> Project
  -> Repository
  -> Scan
  -> ScannerRun
  -> Finding
  -> FindingInstance / FindingEvent / FindingReference
```

The important distinction is:

- `Finding`: long-lived deduplicated issue record
- `FindingInstance`: occurrence of that issue in a specific scan

## Operational Notes

- Auth is JWT-based and currently wired for Neon Auth claims verification.
- Internal worker routes are protected with `INTERNAL_API_KEY` service auth.
- Artifact downloads are exposed through presigned URLs generated by the API.
- Queue communication currently assumes Upstash Redis REST semantics rather than raw Redis TCP.
