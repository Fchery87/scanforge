## Deployment topology (from configuration, not observed)

- [render.yaml](../render.yaml): the API web service, a weekly maintenance cron, and a per-minute `scanforge-scan-dispatch` cron. No worker or scheduler service runs on Render.
- Scanner execution runs on a dedicated Linux host per organization ([ADR-009](adr/ADR-009-dedicated-workers-for-private-beta.md), [ADR-011](adr/ADR-011-beta-executor-and-github-ingress.md)), supervised by [scanforge-worker.service](../infra/worker/scanforge-worker.service) and provisioned by [provision_worker_host.sh](../scripts/provision_worker_host.sh).
- The Next.js app deploys to Vercel ([notes](../infra/vercel/vercel-notes.md)). Redis Streams and R2 layouts are described in [infra](../infra).
- CI is the Git-root workflow `../.github/workflows/ci.yml`. The nested `.github/` (Dependabot/Renovate) is not at the repository root, and GitHub may not read it; this is unverified.

## Scan and finding flow

A manual request or default-branch push enters the [scan routes](../apps/api/app/api/v1/routes/scans.py) or webhooks and the [lifecycle service](../apps/api/app/services/scan_lifecycle.py). The API persists the scan and a dispatch obligation; the dispatcher enqueues it. The worker retrieves API-owned context, fetches and verifies the exact commit, runs adapters, sanitizes and uploads artifacts, normalizes outputs, and submits completion evidence.

[API completion](../apps/api/app/services/scan_completion.py) derives completeness and closure eligibility server-side ([evidence contract](../apps/api/app/services/evidence_contract.py)) and commits evidence with a replay receipt. [Finding persistence](../apps/api/app/services/findings.py) separates canonical findings from occurrences; [lifecycle policy](../apps/api/app/services/finding_lifecycle.py) records qualifying absences only for full scans with every expected scanner healthy and an analyzer comparable to the one that last observed the finding, and closes a finding after two distinct-commit absences on every observed branch. Dependency findings additionally need inventory evidence from the same scan (G1).

## Supported capability matrix

Server-side policy: [beta_capabilities.py](../apps/api/app/core/beta_capabilities.py). "Enabled" means reachable, not release-verified.

| Capability | State | Notes |
| --- | --- | --- |
| Manual full / dependency / secret scans | Enabled | Full scans run five scanners: Trivy (primary dependency engine), Syft (inventory), Gitleaks, Semgrep, Checkov. OSV-Scanner and Grype are registered and shipped in the scanner image but run only in explicit dependency scans ([ADR-019](adr/ADR-019-primary-dependency-engine.md), provisional: chosen without the corpus evaluation, which is NOT RUN) |
| Automatic default-branch push scans | Enabled | Via durable dispatch |
| Finding triage, history, assignment | Enabled | |
| PR review, diff scans | Disabled | Shadow review is the next milestone ([ADR-018](adr/ADR-018-developer-first-security-review-direction.md)) |
| FastAPI review pack (`fastapi.v1`) | Shadow PR runs only | Detection-gated context strategy: retrieval of identity/organization-scope dependencies plus three low-confidence Semgrep authorization/tenant-scope questions. Not comprehensive detection; unsupported cases are listed in `UNSUPPORTED_CASES` in [fastapi_pack.py](../apps/worker/app/review_packs/fastapi_pack.py). Pack id, version and rules digest are recorded in the run summary and the Semgrep scanner run metadata |
| Shadow review candidates (active / superseded / outdated / resolved) | Shadow PR runs only | One private record per (repository, PR, fingerprint), reconciled from each current-head run's completion evidence, so pushes, force-pushes, rebases and redeliveries update rather than duplicate. A new head makes open candidates `superseded` until it is analyzed; absence becomes `resolved` only under comparable analysis (same analyzer identity and fingerprint policy as the last observation) with complete capability coverage, otherwise `outdated`. Only `resolved` candidates are remediation evidence; none feed the branch finding lifecycle. Out-of-order guard: the newest head per PR is recorded with GitHub's `pull_request.updated_at`, and a late delivery for an older head is recorded as ignored (`stale_pull_request_head`) and cannot supersede or displace the newer run; if the payload has no timestamp the guard cannot detect order. Not done: an API or view (#50), force-push back to a head whose run was already superseded (the superseded run is returned, not re-run). See [pr_candidates.py](../apps/api/app/services/pr_candidates.py) |
| Shadow result classification (new / existing / unknown) | Shadow PR runs only | Derived on read from per-scan completion evidence (`summary_json.result_index`, `fingerprint_policy`, scanner runs), not from repository findings. Baseline is a ScanForge-scheduled shadow-style full run of the merge-base (`refs/pull/<n>/base`). `existing` = fingerprint present at the baseline under the same fingerprint policy; `new` additionally needs a comparable analyzer for the producing scanner and complete or analyzer-evidenced not-applicable baseline capability coverage; everything else is `unknown` with a reason. Until analyzers report coverage (#45), absence-based `new` is expected to be `unknown`. Not done: changed-line relevance, re-baselining after a failed baseline. See [pr_classification.py](../apps/api/app/services/pr_classification.py) |
| Shadow replay evaluation corpus | Shadow PR runs only | One reference entry per reviewer label (#51), created when a label is set and never from unlabelled candidates. An entry holds only the revision SHAs (head, base, merge-base), scan / candidate / label ids, the fingerprint, the tuning/holdout split and its policy id, and timestamps; it never copies source, snippets, titles, paths or secrets, so it is not source storage. The split is `sha256(policy:repository:PR)` (about 20% holdout), recorded at creation and never recomputed, so a pull request cannot straddle splits and relabelling keeps it. Entries are built and read inside one organization only. **Tenant deletion:** entries carry `ON DELETE CASCADE` to the organization and repository (like candidates and labels), so deleting either removes them. **Retention:** `SHADOW_CORPUS_RETENTION_DAYS` (default 90, **a maintainer decision to confirm**) counted from entry creation; reads exclude expired entries at once and `POST /internal/shadow-corpus/expire` (scheduler credential, idempotent) deletes them. The sweep must be called by the external scheduler; nothing in this repository schedules it. Relabelling does not extend retention. Not done: a read API or export for replay, per-organization retention overrides, SQLite stands in for PostgreSQL in tests so cascades are exercised with foreign keys on, not against a real database. See [shadow_corpus.py](../apps/api/app/services/shadow_corpus.py) |

| Grades, numeric risk scores, policy enforcement | Disabled | Deferred |

## Gaps found during the 2026-11-04 discovery

| ID | Gap | Source |
| --- | --- | --- |
| G1 | Fixed in source (P1.1, #33): an absence earns credit only when the scanner name, version, parser version, rules digest and fingerprint version match the analyzer that last observed the finding; otherwise an `absence_not_credited` event explains why. Residual risk: vulnerability-database (`db_digest`) and image changes are deliberately not compared, so a withdrawn advisory cannot by itself be told apart from a fix by the analyzer signature; dependency findings are therefore gated by inventory (P1.7, #42): absence earns credit only when the Syft inventory of the same scan, complete and from a completed run, no longer lists the affected package version. Matching is by package name (case, `_`/`.`/`-` and Maven `group:artifact` folded) and exact version, ignoring path and ecosystem, so it errs toward withholding credit; a package still installed records `absence_not_credited` (`package_still_installed`, with the matching packages) and missing, failed, truncated (over 20,000 packages) or malformed inventory records `inventory_unavailable`. Version spellings that differ between Trivy and Syft (for example Debian epochs) can still read as removed, and Syft license findings and non-dependency findings are exempt. Was: a rules/parser/fingerprint-policy change could produce two absences and close a finding as `fixed` | [findings.py](../apps/api/app/services/findings.py) `mark_not_observed_after_scan`; [finding_lifecycle.py](../apps/api/app/services/finding_lifecycle.py) |
| G2 | Fixed in source for Semgrep, Checkov and Gitleaks (P1.5, #38; fp.v3, scanner-level policy versions in `SCANNER_FINGERPRINT_VERSIONS`): identity is repository + rule + path + normalized-snippet digest + occurrence index, with no line numbers and no secret-derived material. Existing fp.v2 findings are kept and never closed by fp.v3 absences (P1.1); they stay open as `analyzer_not_comparable` until re-observed, and re-observation creates a new fp.v3 finding. #40: when a new fp.v3 finding exactly matches an fp.v2 finding (same scanner, rule, path and recorded location; for dependencies same scanner, ecosystem, package, installed version and advisory) the API links them both ways in finding metadata and events (`predecessor_linked`, `successor_linked`) inside the repository only; ambiguous matches stay unlinked, dispositions never transfer, and the finding timeline explains links and `absence_not_credited` events. Legacy fp.v2 rows recorded no snippet digest, so location stands in for it on the legacy side. `apps/api/scripts/link_fp_successors.py` is the repeatable backfill and prints linked, unlinked and preserved counts. Was: Semgrep and Gitleaks fingerprints included line numbers; moved code created a new finding while the old one accrued absences | [identity.py](../apps/worker/app/normalizers/identity.py), [semgrep.py](../apps/worker/app/normalizers/semgrep.py), [gitleaks.py](../apps/worker/app/normalizers/gitleaks.py) |
| G3 | Fixed in source for dependency findings (P1.5 dependency slice, #39): vulnerability fingerprints are `fp.v3` = repository + ecosystem + package + installed version + advisory + scanner, so same-named packages in different ecosystems and results from different scanners never share a finding; cross-scanner merging goes only through `SCANNER_EQUIVALENCE`, which is empty. The same advisory in two manifests stays one finding with two instances. Existing `fp.v2` dependency rows are preserved; because analysis is now under `fp.v3`, their absences are uncredited (`absence_not_credited`) and they never auto-close. Consequence: on first scan after rollout each existing dependency finding is reported again under a new `fp.v3` identity (dispositions do not transfer), and the `fp.v2` row stays open until a human resolves it or the exact-match successor link (#40) is recorded for it; the link never transfers a disposition. Explicit dependency scans still run Trivy, OSV and Grype, now as separate findings. Was: Trivy, OSV and Grype share identical dependency fingerprint inputs without ecosystem or scanner, implicitly merging cross-scanner results (ADR-014 requires tested equivalence) | [dependency_identity.py](../apps/worker/app/normalizers/dependency_identity.py), [canonical_findings.py](../apps/api/app/schemas/canonical_findings.py) |
| G4 | Fixed in source (P1.2, #34): git subprocesses get a private per-scan `HOME`, `GIT_CONFIG_NOSYSTEM`, `GIT_CONFIG_GLOBAL=/dev/null`, no terminal prompts, hooks and fsmonitor disabled, LFS smudge skipped, and only HTTPS transport (file transport only in non-customer fixture mode). Was: host Git filters or URL rewrites could apply to untrusted checkouts | [proc_env.py](../apps/worker/app/security/proc_env.py) `build_git_env`, [execution.py](../apps/worker/app/services/scan_pipeline/execution.py) |

Caveat: the API does not resolve a SHA for manual or scheduled scans that omit `commit_sha` (only push webhooks carry `after`), so those scans now fail at the worker with an explicit error instead of scanning the branch tip. API-side resolution at scan creation is open work | [execution.py](../apps/worker/app/services/scan_pipeline/execution.py) `prepare_repository`; [scans.py](../apps/api/app/services/scans.py) |
